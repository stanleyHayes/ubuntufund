# Account identity publication — 13 September 2026

Engineering controls now cover effective account identity edits and changing an existing private profile to public. Initial registration/legacy identity and all public projections remain separate open requirements.

## Comment attribution checkpoint

New comment admission now includes the displayed account name and avatar, instead of reviewing only the comment body. The existing fingerprint binds these values to actor/action/campaign; changing a registration name or avatar changes the version needing approval. Avatar-bearing submissions stay in the staff media queue. Public name and comment are the only structured text fields; private email/profile/credential fields are excluded. The author identity is re-read after screening and a mismatch denies insertion. Admin/web/native review evidence displays the structured fields.

Seventeen publication integration tests pass, including held public name/avatar, approved resubmission, private-field exclusion and identity mutation during screening. Eight admin and seven web review tests plus API/admin/web/native types/lint pass. Logs `/tmp/ujimora-comment-attribution-{tests,admin,web,checks}.log`. This covers new comment admission only: dynamic author reads, legacy comments, other registration-name projections, immutable avatar bytes, native rendering and final transaction fencing remain open. The post-screening read is not an atomic guarantee against a subsequent identity change.

## Admission and privacy

- `MongoAccountProfileWrite` assembles the full proposed name, avatar, cover, country and profile-page visibility before any account/profile edit. The publication fingerprint binds actor, account, original identity/visibility and a dedicated identity revision. An unchanged field included in a stale request still receives the final version comparison; it cannot bypass review by appearing unchanged before a concurrent edit.
- Automated screening is optional. Without consent, with media, or on flagged/unavailable screening, a proposed version stays in the private review queue. Only an approved exact version can be applied. Phone numbers, account biography, preferences, email and financial data are excluded from the screening text and private publication evidence. Creator biography is a separate public field covered by creator admission.
- Final transaction checks the original identity/visibility version, current credential version, account existence, agreement and publishing restriction. It preserves independent private patches and existing financial/verification/organization-identity fields. Private-to-public changes review the current complete identity; setting visibility false does not require review and invalidates previous-version approvals.
- Pure phone/biography/preferences changes bypass publication screening. The agreement/restriction classifier now identifies country as an identity field and no longer misclassifies account biography as public content. Read tracing found that account biography is returned by authenticated account endpoints, not the public profile DTO. User-report snapshots no longer copy this nonpublic biography into moderation evidence.
- Authenticated profile routes and public profile detail responses use `Cache-Control: private, no-store`. This does not by itself prove every identity projection respects privacy, blocking and moderation; those paths remain under audit.

## Interfaces

Web and native profile forms show explicit unchecked screening consent and preserve held drafts with publication review history. Image editing explains staff review, retains the selected URL and only applies it after a successful save. A delayed image validation cannot submit after its editor is unmounted. Account-keyed forms ignore late results before changing the cached account name/session.

Web Settings explains private-to-public review, sends consent only on publication attempts, rolls a held switch back to its server-confirmed private state and allows exact resubmission after checking the existing review list. Hiding remains immediate. Admin profile editing has the same optional identity screening and opens its staff review queue in a separate tab so the form draft remains available.

Web, native and admin private contact saves omit unchanged identity fields, so a publishing restriction does not block them. Web and admin omission behavior is covered by focused tests.

## Public member-profile access follow-up

`GET /users/:id/public` now reads an optional authenticated viewer and checks the existing bilateral block repository before returning identity. A block in either direction denies the read with 404; removing only one of two reciprocal blocks does not restore access. Guests retain access to public profiles. The subsequent shared visibility correction below now returns 404 for private profiles as well. Closed accounts and malformed identifiers return 404. The route applies `private, no-store` before authentication/controller processing, including denied responses.

Web and native member-profile hooks bind results to both viewer and target, ignore late responses from the old scope, and clear identity on failed refreshes. Web refreshes on focus/visibility and every 30 seconds while visible; native refreshes on screen focus/app activation and every 30 seconds while active. This is bounded refresh, not immediate server push invalidation. Initial missing-profile behavior remains public for compatibility and requires the registration/legacy rollout decision.

Verification: 17 API tests across public-profile access, account admission and atomic profile patches pass, plus API type/lint. Five web hook/privacy tests pass, including scope switches, stale responses and denied focus refreshes. Web/native type and lint checks pass, and the web build passes. Final iOS/Android/web export passes, including resetting the native navigation title when identity becomes unavailable. Physical native runtime remains an external gate. This does not yet resolve organization projections, identity embedded in other public content, or every projection of restricted-account identity. Apple 1.2 and Google UGC blocking requirements were rechecked on 13 September 2026: [Apple](https://developer.apple.com/app-store/review/guidelines/#user-generated-content), [Google](https://support.google.com/googleplay/android-developer/answer/9876937?hl=en-GB). ## Organization and restricted-profile visibility

The shared `MongoPublicProfileVisibility` adapter excludes closed/nonexistent, explicitly private, restricted and bilaterally blocked account identities. Member-profile detail and organization directory, ID/slug detail and organization campaign-list reads now use this boundary. Public denial is 404, including private member profiles, superseding the earlier 403 behavior. Organization list filtering happens before serialization; guest discovery remains available for eligible accounts. Missing legacy profile records continue to be public, pending the registration/legacy admission rollout. These public reads confer no owner/admin bypass; authenticated account settings and staff tools are separate.

Public organization summaries/details no longer include the login email. Registration numbers and private biography/contact fields remain absent. This intentionally does not introduce a public contact-email field without an explicit publication choice. Visibility reads do not alter stored accounts, campaign funds or financial records.

Web directory/detail components are keyed by viewer (and detail target), ignore old responses, and revalidate on focus and every 30 seconds while visible. Detail and campaign reads must both succeed before the combined result is applied; denied reloads clear identity/images/campaigns, close the image editor and remove identity SEO metadata. Native organization screens use `usePublicRead` to scope results by viewer/target/retry, revalidate on focus/app activation and periodically while active, clear denied results, and reset unavailable navigation titles. These are bounded refresh controls, not instantaneous server-push revocation.

## Restricted authors in campaign discussions and updates

`hiddenContentAuthorIds` applies closure, restriction and bilateral-block checks without treating a private profile page as withdrawal of separately published contributions. Comment and update list use cases apply this policy before public serialization. Restricting an author suppresses their other contributions, not only the item that prompted the report. Removing the restriction restores only otherwise eligible records; individually deleted/moderated items remain hidden. Source comments/updates, campaign balances and staff evidence are retained. Closed and nonexistent authors are excluded; failed visibility evidence fails the request instead of returning unchecked content. Comment/update routes apply `private, no-store`, including failures.

Web/native discussion components refresh on focus/app activation and periodically while visible/active. Failed loads clear displayed comments. A request revision prevents a pre-block/delete/post list response from restoring obsolete state; native reload errors are inline instead of repeated modal alerts. Updates use scoped refreshes; the native update component shares `usePublicRead`. A profile-page privacy change alone does not remove comments, matching the disclosed behavior.

## Donation REST identity projections

Recent-donation DTOs now omit account IDs for anonymous donations. Both recent and campaign donation lists apply current closed/restricted/bilateral-block author eligibility. Ineligible identities are rendered anonymously; campaign rows omit the donor photo and message. Donation IDs, amounts, currency, row counts and campaign balances remain intact. Staff restriction removal restores otherwise eligible identity; private donor history remains authenticated and unchanged. The separate private profile-page flag does not withdraw an intentionally public donation. Guest IDs are not passed to Mongo user lookup. The recent feed now uses optional viewer authentication, and both route families use `private, no-store`.

Web campaign history, compact live donation lists and global activity use a shared viewer/path-scoped authoritative REST hook. SSE events schedule a throttled re-fetch rather than copying stale event payload identity into the display. Focus and 30-second visible polling revalidate existing rows; denied requests clear cached results; old-viewer promises are ignored. The global component's previously unbacked campaign-created/milestone event rows are no longer inserted from arbitrary event payloads; its rendered source is the current recent-donation endpoint. This change does not claim server-side event payloads are fully safe. Native campaign previews already re-fetch the campaign and paginated donations on focus/app activation/active polling; that existing path consumes the newly redacted DTO.

### Comment commit checks

Comment insertion now shares a transaction with current account credentials, public author identity, campaign access and exact publication approval. Block/unblock changes now write both participant accounts in the relationship transaction; the concurrency follow-up is recorded in PUBLICATION_SCREENING_AUDIT.md.

New comments persist the exact admitted author name/photo with the comment. DTOs use that snapshot rather than the current account profile. Legacy comments without a snapshot display `Community member` and no photo; no unreviewed identity is backfilled. Current restricted/closed/blocked-author filtering remains in force. Safety reports preserve the displayed snapshot alongside comment text, rather than borrowing later profile identity. Account cleanup removes snapshot fields from all comments, including previously hidden comments, while retaining the existing soft-deletion behavior.
